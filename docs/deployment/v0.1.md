# Jarvis Command v0.1 deployment

This runbook deploys the read-only first slice. Secrets are represented as `[REDACTED]`; real values live only in mode-`0600` environment files.

## Runtime topology

1. Cloudflare Access and Tunnel terminate the public request.
2. `jarvis-command-jwks.timer` atomically refreshes Cloudflare's public Access signing keys into a host-owned cache on VM 113.
3. `jarvis-command-app.service` starts the app only after the egress policy is active. The container reads the signing-key cache through a read-only bind mount, runs with host networking, and binds only `127.0.0.1:3000` on VM 113.
4. `jarvis-command-bridge.service` runs on the Hermes host and creates a reverse SSH forward bound only to `127.0.0.1:18642` on VM 113.
5. `jarvis-command-read-proxy.service` starts the read proxy only after its host egress policy is active; the proxy binds only `127.0.0.1:8643` on the Hermes host.
6. The official Hermes API binds only `127.0.0.1:8642`.

The reverse forward is deliberate. The Internet-facing VM receives only the narrow read-proxy credential; it holds no SSH key capable of initiating a connection into the Hermes host and never receives `API_SERVER_KEY`. A dedicated Hermes-host key may open exactly one remote loopback listener on VM 113. If the tunnel dies, the BFF degrades to an offline snapshot.

Host networking is retained solely so each process can reach its host's loopback-only peer. It is paired with fixed unprivileged UIDs and `jarvis-command-egress.service`: UID `10001` may initiate connections only to `127.0.0.1:{3000,18642}`, and UID `10002` only to `127.0.0.1:{8642,8643}`. Established replies remain permitted. All other new IP traffic from those UIDs is rejected. Docker restart policies are disabled. The two container units require, bind to, are `PartOf=`, and install as `WantedBy=` the standalone egress unit. The stock global `nftables.service` is not part of that lifecycle and remains dormant on the production hosts. Its installed drop-in refuses start, stop, and reload before they can apply `/etc/nftables.conf` or flush globally; egress startup rejects failed, transitional, or enabled/inactive global-service states. The BFF never fetches remote signing keys itself: a separate hardened host oneshot/timer writes a validated last-known-good JWKS atomically, and the BFF reloads that local file for every assertion.

## Build and freeze the candidate

Build only a clean, reviewed commit. Compose requires explicit image values, and `deploy/validated-compose-up.sh` rejects mutable names/tags, missing local images, Compose resolution drift, stopped or unhealthy workloads, and post-start container identity mismatches before accepting a deployment. It uses Compose's health wait, independently verifies image/running/health state, notifies systemd only after verification, and then continuously rechecks identity, running state, and health so a later unhealthy or stopped container fails the unit and enters systemd recovery. Cleanup traps cover ordinary errors and `HUP`/`INT`/`TERM`; `ExecStopPost=` is the final idempotent guard for failed activation. A partial Compose start or failed verification triggers a stop plus a second running-state check; cleanup failure is reported rather than disguised as success.

```bash
npm ci
npm test
npm run typecheck
npm run lint
npm run build
npm run test:e2e
npm audit --audit-level=high --omit=dev

test -z "$(git status --porcelain)"
RELEASE_ID=$(git rev-parse --verify HEAD)
docker build --provenance=false -t "jarvis-command-app:${RELEASE_ID}" -f Dockerfile .
docker build --provenance=false -t "jarvis-command-read-proxy:${RELEASE_ID}" -f Dockerfile.read-proxy .

APP_IMAGE_ID=$(docker image inspect --format '{{.Id}}' "jarvis-command-app:${RELEASE_ID}")
READ_PROXY_IMAGE_ID=$(docker image inspect --format '{{.Id}}' "jarvis-command-read-proxy:${RELEASE_ID}")
[[ ${APP_IMAGE_ID} =~ ^sha256:[0-9a-f]{64}$ ]]
[[ ${READ_PROXY_IMAGE_ID} =~ ^sha256:[0-9a-f]{64}$ ]]
```

- both Compose services use read-only roots, no capabilities, no-new-privileges, PID/memory/CPU ceilings, and host networking
- app runtime contains Fastify/Jose/Zod/static serving but no React build dependencies
- read-proxy runtime contains only its Fastify/Zod dependency closure; no Jose, static plugin, React, or workspace source packages

## Install the egress policy on both hosts

Install the `nftables` package and the standalone Jarvis policy before starting either production container. Run this block independently on each host from its private, checksum-verified release stage. Do not enable or start `nftables.service` solely for Jarvis Command; on Docker/Tailscale hosts the stock global `flush ruleset` can discard dynamically managed rules.

```bash
sudo install -d -m 0755 /etc/jarvis-command /usr/local/libexec /etc/systemd/system/nftables.service.d
sudo install -m 0644 deploy/jarvis-command-egress.nft /etc/jarvis-command/jarvis-command-egress.nft
sudo install -m 0755 deploy/apply-nftables-ruleset.sh /usr/local/libexec/jarvis-command-apply-nftables
sudo install -m 0644 deploy/50-jarvis-command-nftables.conf /etc/systemd/system/nftables.service.d/50-jarvis-command.conf
sudo install -m 0644 deploy/jarvis-command-egress.service /etc/systemd/system/jarvis-command-egress.service
sudo unshare --net /bin/sh -c '/usr/sbin/nft add table inet jarvis_command_egress && /usr/sbin/nft --check -f /etc/jarvis-command/jarvis-command-egress.nft'
sudo systemctl daemon-reload
sudo systemctl enable --now jarvis-command-egress.service
sudo systemctl is-active jarvis-command-egress.service
sudo nft list table inet jarvis_command_egress
```

The standalone egress unit deletes and recreates only its own table in one nftables transaction. The installed drop-in does not activate the stock nftables service; it overrides stock start, stop, and reload so each operation fails before a base apply or global `flush ruleset`. The egress preflight accepts only a stable active nftables service or the normal disabled/masked and inactive state. Failed, reloading, activating, deactivating, and enabled-but-inactive states keep egress and its dependent containers down.

Do not mutate `nftables.service` through the Jarvis release path. An independently managed active nftables host requires a separate, host-specific maintenance transaction: stop and verify every Jarvis workload, preserve or deliberately stop Docker and Tailscale, perform the host firewall work, restore and verify their dynamically managed tables, then restore and verify Jarvis egress before its containers. Temporarily removing the drop-in is part of that controlled maintenance—not an installation shortcut. Direct `/usr/sbin/nft -f /etc/nftables.conf` or `nft flush ruleset` bypasses the guard and is prohibited while either constrained container is active.

The numeric UIDs are part of the security boundary. Do not assign host users or unrelated containers to `10001` or `10002`.

Install the immutable-image deployment guard on both hosts:

```bash
sudo install -d -m 0755 /usr/local/libexec
sudo install -m 0755 deploy/validated-compose-up.sh \
  /usr/local/libexec/jarvis-command-validated-compose-up
```

## Install the Cloudflare JWKS cache on VM 113

The cache updater—not the BFF—has outbound HTTPS access. It accepts strict RFC 8259 JSON only, requires unique key IDs, verification-only operations, valid `ext` semantics, public-only RS256 material, canonical base64url RSA parameters, 2048–8192-bit odd moduli, and sane odd exponents. Every candidate public key must also import successfully through OpenSSL before the script atomically replaces `certs.json`. A failed refresh leaves the last known good file byte-for-byte untouched.

```bash
sudo install -d -m 0755 /etc/jarvis-command /var/lib/jarvis-command/cloudflare-jwks /usr/local/libexec
sudo install -m 0755 deploy/refresh-cloudflare-jwks.sh \
  /usr/local/libexec/jarvis-command-refresh-cloudflare-jwks
sudo install -m 0644 deploy/jarvis-command-jwks.service deploy/jarvis-command-jwks.timer \
  /etc/systemd/system/
sudo install -m 0644 /path/to/completed/cloudflare-jwks.env \
  /etc/jarvis-command/cloudflare-jwks.env
sudo systemctl daemon-reload
sudo systemctl start jarvis-command-jwks.service
sudo test -s /var/lib/jarvis-command/cloudflare-jwks/certs.json
sudo systemctl enable --now jarvis-command-jwks.timer
sudo systemctl is-active jarvis-command-jwks.timer
```

Set `CF_ACCESS_JWKS_FILE=/run/jarvis-command/cloudflare-jwks/certs.json` in `app.env`. The Compose bind mount is read-only. Do not add general DNS or HTTPS egress to UID `10001` as a shortcut.

## Install the Hermes-host components

The unrestricted upstream Hermes credential must never be enabled from an inherited or permissively owned file. The descriptor-safe helper walks every path component without following symlinks, opens the source once with `O_NOFOLLOW|O_NONBLOCK`, validates that same descriptor with `fstat`, and atomically installs bytes from that descriptor as `root:root 0600`. This closes special-file, ancestor-symlink, and check/use substitution paths.

```bash
READ_PROXY_ENV_SOURCE=/path/to/completed/read-proxy.env
OPERATOR_UID=$(id -u)

sudo install -d -o root -g root -m 0755 \
  /srv/jarvis-command-read-proxy /etc/jarvis-command /usr/local/libexec
sudo install -m 0755 deploy/secure-env-file.py /usr/local/libexec/jarvis-command-secure-env-file
sudo test "$(sudo stat -c %u:%g:%a /usr/local/libexec/jarvis-command-secure-env-file)" = 0:0:755
sudo /usr/local/libexec/jarvis-command-secure-env-file install "${READ_PROXY_ENV_SOURCE}" /etc/jarvis-command/read-proxy.env "${OPERATOR_UID}"
sudo test -f /etc/jarvis-command/read-proxy.env
sudo test ! -L /etc/jarvis-command/read-proxy.env
sudo test "$(sudo stat -c %u:%g:%a /etc/jarvis-command/read-proxy.env)" = 0:0:600

(
  set -Eeuo pipefail
  release_stage=''

  cleanup_release_env() {
    local cleanup_status=$?
    local cleanup_failed=0
    trap - EXIT HUP INT TERM
    if [[ -n ${release_stage} && ${release_stage} =~ ^/tmp/jarvis-command-read-proxy\.[A-Za-z0-9]{10}$ ]]; then
      if ! rm -rf -- "${release_stage}"; then
        cleanup_failed=1
      elif [[ -e ${release_stage} ]]; then
        cleanup_failed=1
      fi
    elif [[ -n ${release_stage} ]]; then
      cleanup_failed=1
    fi
    if (( cleanup_failed != 0 )); then
      printf 'release metadata staging cleanup failed\n' >&2
      (( cleanup_status != 0 )) || cleanup_status=1
    fi
    exit "${cleanup_status}"
  }

  trap cleanup_release_env EXIT
  trap 'exit 129' HUP
  trap 'exit 130' INT
  trap 'exit 143' TERM

  release_stage=$(mktemp -d /tmp/jarvis-command-read-proxy.XXXXXXXXXX)
  [[ ${release_stage} =~ ^/tmp/jarvis-command-read-proxy\.[A-Za-z0-9]{10}$ ]]
  chmod 0700 "${release_stage}"
  release_stage_metadata=$(stat -c '%u:%a' -- "${release_stage}")
  [[ ${release_stage_metadata} == "${OPERATOR_UID}:700" ]]
  printf 'JARVIS_COMMAND_APP_IMAGE=%s\nJARVIS_COMMAND_READ_PROXY_IMAGE=%s\n' \
    "${APP_IMAGE_ID}" "${READ_PROXY_IMAGE_ID}" > "${release_stage}/release.env"
  chmod 0600 "${release_stage}/release.env"
  sudo /usr/local/libexec/jarvis-command-secure-env-file install \
    "${release_stage}/release.env" /etc/jarvis-command/release.env "${OPERATOR_UID}"
  sudo test "$(sudo stat -c %u:%g:%a /etc/jarvis-command/release.env)" = 0:0:600
  sudo cmp -s "${release_stage}/release.env" /etc/jarvis-command/release.env
)

sudo install -m 0644 deploy/read-proxy.compose.yaml /srv/jarvis-command-read-proxy/compose.yaml
sudo install -m 0644 deploy/jarvis-command-read-proxy.service /etc/systemd/system/jarvis-command-read-proxy.service
sudo install -m 0644 deploy/jarvis-command-bridge.service /etc/systemd/system/jarvis-command-bridge.service
sudo systemctl daemon-reload
sudo systemctl enable --now jarvis-command-read-proxy.service
sudo systemctl enable --now jarvis-command-bridge.service
```

The official API environment change requires a Hermes gateway restart from outside the gateway process. After restart, verify:

```bash
ss -ltn '( sport = :8642 or sport = :8643 )'
curl -fsS http://127.0.0.1:8643/_health

test "$(docker inspect --format '{{.Image}}' jarvis-command-read-proxy)" = "${READ_PROXY_IMAGE_ID}"
```

Both listeners must be loopback-only.

## Transfer and install the app image

Treat transfer, privileged installation, and cutover as one guarded transaction. `deploy/release-app.sh` arms local cleanup before creating a stage, streams `deploy/allocate-release-stage.sh` over the authenticated SSH session, and accepts a remote stage record only after fail-closed `0700` ownership validation. A descriptor-safe copy moves `app.env` into the private local stage; every artifact is checksummed and copied directly into the private unpredictable remote stage. `deploy/install-app-release.sh` arms cleanup before validating its inherited stage, installs and reads back the artifacts, and only then invokes cutover. All three scripts preserve the original error or signal status, report cleanup failures, and attempt cleanup on success, ordinary failure, `HUP`, `INT`, and `TERM`. No root operation consumes a shared predictable `/tmp` pathname.

```bash
APP_ENV_SOURCE=/path/to/completed/app.env
SSH_TARGET=neal@192.168.6.113
SSH_KEY=/home/neal/.ssh/jarvis_homelab_ed25519
SSH_OPTIONS=(-i "${SSH_KEY}" -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes)

CUTOVER_STATE_DIR=$(deploy/release-app.sh \
  "${APP_ENV_SOURCE}" "${SSH_TARGET}" "${SSH_KEY}" \
  "${APP_IMAGE_ID}" "${READ_PROXY_IMAGE_ID}")
[[ ${CUTOVER_STATE_DIR} =~ ^/var/backups/jarvis-command/cutover-[0-9]{8}T[0-9]{6}Z$ ]]
```

The guarded operation does **not** start the application unit directly. The current `jarvis-command-bootstrap` container owns `127.0.0.1:3000` with restart policy `unless-stopped`; only the cutover helper may hand off that port. The helper captures the bootstrap image identity, restart policy, Compose labels, supervisor state, and root artifact under the returned mode-`0700` state directory. It changes the bootstrap restart policy to `no` before stopping it, proves port `3000` is unbound, starts the monitored app unit, and verifies the exact app image, running/healthy state, local health endpoint, and non-bootstrap Jarvis Command root. Any failure during those steps automatically restores and verifies the original bootstrap lifecycle. Keep `CUTOVER_STATE_DIR` and the stopped bootstrap container until the authenticated public and reboot gates pass.

If any subsequent public/browser/reboot gate fails, roll back immediately from the same operator shell:

```bash
printf -v cutover_state_q '%q' "${CUTOVER_STATE_DIR}"
ssh "${SSH_OPTIONS[@]}" "${SSH_TARGET}" "sudo -n /usr/local/libexec/jarvis-command-cutover-app rollback ${cutover_state_q}"
```

The guarded transaction removes its private local and remote staging directories as soon as the cutover command returns. Rollback relies on the loaded immutable image and the returned root-owned cutover state, not on transfer copies.

## Android sideload release

Jarvis Command v0.1 also ships as the signed TWA package `com.kumargg.jarviscommand`. The web origin remains the application and authorization boundary; the APK supplies launcher identity, trusted-origin verification, splash/icon resources, and browser-mediated presentation without embedding a generic WebView.

The Android release certificate is public identity metadata, not a secret:

```text
SHA-256 62:1C:87:98:E1:AF:33:0A:60:AA:7F:1B:8B:B7:68:9B:BC:9C:66:2C:B1:8B:94:A7:E8:9F:0E:5F:07:C1:34:D0
```

Private signing material remains outside the repository under `/home/neal/.config/jarvis-command/android/` at mode `0600`. Preserve it for every update; a different certificate cannot upgrade an installed package with the same application ID.

Before building the APK:

1. Include `apps/web/public/.well-known/assetlinks.json` in the exact reviewed web candidate.
2. Deploy the association bytes and read-only compose mount while preserving the currently approved immutable app image:

   ```bash
   APPROVED_APP_IMAGE_ID=sha256:2fd64f267f33feeb6a17a20e37b2a6594e3398817ba114b8ead13bc949cfe654
   deploy/release-android-association.sh "$SSH_TARGET" "$SSH_KEY" "$APPROVED_APP_IMAGE_ID"
   ```

   The publisher and root helper both reject any other image digest. The helper is streamed directly into noninteractive `sudo`; it copies the unprivileged stage through single-open descriptors into a private root-owned snapshot and requires separately supplied reviewed SHA-256 values before consuming those bytes. Record the returned `/var/backups/jarvis-command/association-<UTC timestamp>` directory. The helper captures the prior compose/runtime, recreates only `jarvis-command-app`, proves the image ID did not change, verifies health, and compares the locally served association bytes to the reviewed file. Any failure automatically restores the prior compose and runtime. The general app-image release does not carry `assetlinks.json`; this remains a separate recoverable transaction.
3. Create a separate Cloudflare Access self-hosted application whose domain is `command.sharma-house.com/.well-known/assetlinks.json`; attach one `Bypass` policy with `Include: Everyone` to that file-path application. Never add that bypass or an `Everyone` rule to the parent Jarvis Command application.
4. Cloudflare path applications also govern descendants even when the configured file path has no wildcard. Create a second, more-specific self-hosted application for `/.well-known/assetlinks.json/*` and attach a `Block` policy with `Include: Everyone`. Cloudflare documents that this wildcard covers descendants but not the parent file, so the exact association remains public while suffix paths fail closed.
5. Prove anonymous `GET` and `HEAD` for the exact file return the reviewed JSON and do not redirect to Access.
6. Prove anonymous `/`, `/api/health`, `/api/bootstrap`, and a neighboring `/.well-known/` path remain protected by the parent Access application. Probe `/.well-known/assetlinks.json/test` separately and require an Access redirect or block response—not application content.

Build and verify the signed APK:

```bash
deploy/build-android-release.sh
```

The gate runs Gradle tests, Android lint, R8, and signed release assembly; verifies the APK package, version, SDK levels, certificate fingerprint, and permission boundary; and emits the artifact path and SHA-256. Distribute only `dist/android/jarvis-command-v0.1.0.apk` from that final post-review build.

- Android reports package `com.kumargg.jarviscommand` at version `0.1.0` / code `1` signed by the recorded certificate;

- Wi-Fi and cellular launches both reach the same protected production origin.

If domain verification fails, leave the web application protected and stop: the Custom Tab fallback is safe but not release acceptance. Removing the exact Digital Asset Links association revokes full-screen trust without exposing the application; ordinary Access protection remains authoritative.

## Rollback

1. For an Android association release rollback, use the validated state directory returned by `release-android-association.sh`:

   ```bash
   ssh "${SSH_OPTIONS[@]}" "$SSH_TARGET" \
     sudo -n /usr/bin/bash -s -- rollback "$ASSOCIATION_STATE_DIR" \
   ```
